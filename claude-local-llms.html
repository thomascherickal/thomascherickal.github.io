01Introduction: Why Local LLMs Matter Now

By the end of this guide you will have a language model running on your own Linux machine and connected to two coding agents, OpenCode and Claude Code. You will also know which model fits the hardware you already own, what the next hardware step costs in October 2026, and when paying for Claude's API is still the cheaper option.

Running a model locally means the weights sit on your disk and your GPU or CPU computes every token. A prompt goes nowhere unless you send it somewhere. Two changes this year made the setup far more practical. In January, Ollama 0.14 added Anthropic Messages API compatibility, and LM Studio, vLLM and llama.cpp now ship their own /v1/messages endpoints, so Claude Code can talk to a local server after you set three environment variables. Small models also improved. Alibaba reports that Qwen3.8-27B scores 61.7 on SWE-bench Pro when run inside the Claude Code harness, and Ollama packages it as an 18 GB download.

Hardware is the constraint. A memory shortage has pushed GPU and unified-memory prices far above their launch levels. The RTX 5090 launched at $1,999, yet its lowest new asking price in the US was $4,920.99 on 11 October, and the cheapest card in stock in India costs about ₹7.49 lakh. Every tier in this guide carries a current price so you can decide with real numbers rather than launch-day ones.

The sections below cover six model families from 8B to 120B parameters, five runtimes, the OpenCode and Claude Code setups, and six tutorials split into basic, intermediate and advanced levels. Five small tools run in the page itself: a memory calculator, a break-even calculator, a model picker, a config generator and a tutorial filter. None of them sends data anywhere. Commands target Ubuntu and Debian, with Fedora and Arch notes only where a command changes.

02Advantages, Trade-Offs And Cost Savings

These are the advantages that hold up in practice:

  • Privacy and data residency: source code, contracts and customer records stay on hardware you own, and no third-party processor sits in the request path.
  • Offline use: a laptop on a train or a machine in an air-gapped lab behaves exactly as it does on the office network.
  • No rate limits: a batch job runs as fast as your GPU allows, with no HTTP 429 responses and no quota resets to wait for.
  • Predictable cost: the hardware is a one-off purchase, and electricity is the only running expense.
  • Latency: there is no network hop, so time to first token depends only on your machine and the prompt length.
  • Customisation: you can fine-tune, change chat templates, pick a quantization and keep one model version for years.
  • Vendor independence: a downloaded Apache 2.0 model such as Gemma 4, gpt-oss or Qwen3.8-27B cannot be withdrawn or repriced.
  • Compliance evidence: an auditor can inspect the exact model file and server version that produced an output.

Open models still trail the frontier. In Pinggy's October 2026 roundup of Artificial Analysis scores, Claude Opus leads at 58, the best open-weight model scores 46, and Qwen3.8-27B, the strongest model that fits one 24 GB card, scores 34. Long agentic sessions expose that gap first, because small errors compound over dozens of tool calls. Maintenance also becomes your job: drivers, CUDA versions, context settings and model updates all need attention.

A Worked Break-Even Example

Take a team of three developers running agentic coding sessions on Claude Sonnet 5.5, which Anthropic's pricing page lists at $2 input and $10 output per million tokens. Agent loops resend a lot of context, so assume 300 million input tokens and 30 million output tokens a month. That is 300 × $2 + 30 × $10 = $900 before prompt caching; cache reads cost $0.10 per million on Sonnet 5.5, so a well-cached workload pays less.

Now buy a 128 GB Framework Desktop for $3,449 and spread it over 36 months, which is $95.81 a month. At an average 200 W for eight hours a day, it draws 48 kWh a month. At the EIA's 2026 US residential average of 18.2 cents per kWh, that is $8.74. In India, using an assumed ₹8 per kWh for a household in a higher consumption slab, it is ₹384. Check your own DISCOM schedule, because slabs vary by state and usage.

A local model will not replace Sonnet 5.5 on every task, so assume it absorbs 60 percent of the tokens. The cloud bill falls to $360 and the team saves $540 a month. The break-even formula is:

months to break even = hardware cost ÷ (monthly cloud savings − monthly electricity)

In the US that gives $3,449 ÷ ($540 − $8.74) = 6.5 months. In India the electricity term is smaller, so the payback is about the same, although import duty raises the hardware price. Run the same arithmetic on Claude Haiku 5.5, priced at $0.10 input and $0.50 output for prompts up to 100,000 tokens, and the picture flips. The whole 330-million-token workload costs $45 a month, a 60 percent shift saves $27, and the box would need more than 15 years to pay for itself. For cheap, short prompts, buy local hardware for privacy or offline needs, not to save money.

03Six Model Families From 8B To 120B

Two terms come up in every row of the table below. A dense model runs every parameter for every token. A mixture-of-experts (MoE) model sends each token through a few expert blocks, so its active parameter count sets the compute per token while its total count still sets the memory it needs. Quantization stores weights in fewer bits: Q4_K_M is a popular 4-bit GGUF format for llama.cpp-based tools, and MXFP4 is the 4-bit format that gpt-oss was trained in.

Qwen

Alibaba released the open weights of Qwen3.8-27B on Hugging Face in August 2026 under Apache 2.0. It is a 27B dense vision-language model with a native context of 262,144 tokens that extends to about one million with YaRN scaling. It thinks before answering by default, and a reasoning_effort setting trades depth for speed. The qwen3.8 entry in Ollama's library lists tools, thinking and vision support at 18 GB. For agentic coding on one 24 GB card it is the default pick in this guide.

Gemma

Google launched Gemma 4 under an Apache 2.0 licence on 2 April 2026. The family includes E2B and E4B edge models, a 26B MoE that activates 3.8B parameters per token and a 31B dense model, and Ollama also carries a 12B tag. The workstation sizes take 256K tokens of context, support native function calling and accept images. The 26B MoE generates faster because so few parameters run per token, while the 31B dense model keeps more quality.

Mistral

Mistral covers both ends of the ladder under Apache 2.0. The Ministral 3 8B model card lists an 8.4B language model plus a 0.4B vision encoder, native function calling and a 256K context window, and says the model fits in 12 GB of VRAM in FP8. A 14B sibling follows the same design. At the top, Mistral Small 4 on Hugging Face is a 119B MoE with 6.5B active parameters, 128 experts and a 256K context, and it merges chat, reasoning and agentic coding into one model.

Llama

Meta's Llama 3.3 70B Instruct is the dense 70B option. It has a 128K context, eight officially supported languages including Hindi, and tool calling. Its licence is the Llama 3.3 Community License, which requires "Built with Llama" attribution and sets a 700-million-monthly-user threshold, so read it before shipping a product. At Q4_K_M it needs about 42 GB for weights alone, which puts it on a dual-GPU build or a 128 GB unified-memory machine.

gpt-oss

OpenAI's two open models ship under Apache 2.0. The gpt-oss-120b model card gives 117B total and 5.1B active parameters for the large model and 21B total and 3.6B active for gpt-oss-20b. Both were post-trained with MXFP4 weights, so the 120B model fits one 80 GB GPU and the 20B model runs within 16 GB. Each exposes low, medium and high reasoning effort and handles function calling. Thanks to that small active count, gpt-oss-120b runs at usable speeds even when most of its experts sit in system RAM, which Tutorial 5 relies on.

Nemotron

NVIDIA's Nemotron 3 Super model card describes a 120B hybrid MoE with 12B active parameters and up to one million tokens of context, released under the NVIDIA Nemotron Open Model License rather than Apache 2.0. The NVFP4 build lists a single DGX Spark as a supported minimum. Choose it for long-document and agent workloads on NVIDIA hardware where the licence suits you.

04The Hardware You Need And What It Costs

Memory decides what you can run, and memory bandwidth decides how fast it runs. A model needs room for three things: the quantized weights, the KV cache that stores attention state for every token in the context, and compute buffers. The llama.cpp guide to running gpt-oss shows the split clearly: gpt-oss-120b needs 61 GB of model data, 2.7 GB of compute buffers and about 0.3 GB of cache per 8,192 tokens, which comes to 64.9 GB at 32K context.

Context length is the setting people forget. Ollama's context-length documentation says it defaults to 4K tokens below 24 GiB of VRAM, 32K between 24 and 48 GiB, and 256K above that, and it recommends at least 64,000 tokens for coding tools. A coding agent sends its system prompt and tool schemas with every request, so a 4K window breaks it.

Indian figures come from GPUPrix listings for the RTX 5060 Ti and the RTX 5090 in India. 05Five Tools That Run LLMs Locally

Each tool below loads model weights, runs them on your GPU and exposes an HTTP API. They differ in interface, API dialect and how many users they serve at once.

Figure 2. The local inference stack. Ollama, LM Studio and Jan wrap llama.cpp; vLLM brings its own high-throughput engine.

Ollama is the quickest start. One script installs a CLI, a background service and a model registry, and ollama run downloads and starts a model in one step. It serves an OpenAI-compatible API under /v1 and, since version 0.14, an Anthropic-compatible one, and its ollama launch command configures Claude Code and OpenCode for you. Ollama's Linux install guide covers NVIDIA and AMD ROCm setups.

LM Studio is a desktop app with a model browser, per-model settings and a headless lms command line for servers. It exposes an OpenAI-compatible API on port 1234, and LM Studio's Claude Code announcement introduced a /v1/messages endpoint in version 0.4.1, documented on its Anthropic compatibility page. It suits people who want to compare quantizations and sampling settings without editing files.

llama.cpp is the engine underneath most desktop tools, and its llama-server binary is the most configurable server here. The llama-server README lists OpenAI-compatible chat, responses and embeddings routes plus Anthropic Messages API compatibility, with a default port of 8080. It builds against CUDA, ROCm or Vulkan, and flags such as --n-cpu-moe let a 120B MoE run on a modest GPU.

vLLM is the throughput option for serving several people at once. It batches concurrent requests on the GPU, serves an OpenAI-compatible API on port 8000, and, per vLLM's Claude Code integration guide, implements the Anthropic Messages API as well. It loads safetensors checkpoints such as FP8 and NVFP4 rather than GGUF files, and it expects a card with enough VRAM for the whole model.

Jan is an open-source desktop chat app built on llama.cpp. Jan's local API server documentation describes an OpenAI-compatible server at 127.0.0.1:1337, and Linux builds come as .deb and AppImage packages. Its docs do not describe an Anthropic endpoint, so pair it with OpenCode or your own scripts rather than Claude Code.

06Local LLMs With OpenCode On Linux

OpenCode is an open-source coding agent for the terminal. It reads your repository, plans changes, edits files and runs commands, and it talks to models through the AI SDK, which lets it use any OpenAI-compatible server. OpenCode's provider documentation shows the exact block for Ollama, LM Studio and llama.cpp: a provider entry that uses the @ai-sdk/openai-compatible package, an options.baseURL pointing at the local server, and a models map whose keys must match the server's model IDs exactly, colons included.

Two settings decide whether the agent works. The first is context. OpenCode sends a long system prompt and tool definitions with each turn, so the server must allow far more than its default; set Ollama to 64K tokens and declare the same limit.context in the config so OpenCode can track how much room is left. The second is tool calling. The agent edits files and runs commands through structured tool calls, and a model that writes a tool call as plain text stalls the loop. OpenCode's docs suggest raising num_ctx first when tool calls fail, then switching to a model with stronger tool calling.

Start with models whose cards list native function calling: Qwen3.8-27B on a 24 GB card, gpt-oss-20b on a 16 GB card, and gpt-oss-120b or Mistral Small 4 on a 128 GB machine. Ollama can also write the config with ollama launch opencode --model qwen3.8, which leaves your own opencode.json untouched. Tutorial 2 builds it by hand so you can see each key.

07Local LLMs With Claude Code And Claude

There are two ways to combine Claude with a local model.

The first runs Claude Code, Anthropic's terminal agent, against a local model instead of Anthropic's API. Claude Code speaks the Anthropic Messages API, and Claude Code's environment variable reference documents ANTHROPIC_BASE_URL for redirecting it. Ollama's Claude Code integration page gives the full setup: set the base URL to http://localhost:11434, set ANTHROPIC_AUTH_TOKEN to ollama, leave ANTHROPIC_API_KEY empty, and start claude --model with a local model name. Claude Code also asks for Opus, Sonnet and Haiku tiers internally, so map all three with ANTHROPIC_DEFAULT_OPUS_MODEL, ANTHROPIC_DEFAULT_SONNET_MODEL and ANTHROPIC_DEFAULT_HAIKU_MODEL.

What works: file reads and edits, shell commands, and multi-step tasks on a repository with a model that has native tool calling and at least 64K of context. What degrades: speed, because local generation is slower than Anthropic's servers; long sessions, where small models lose track sooner; and some hosted features such as Anthropic's server-side web search. vLLM adds one rule of its own: served model names cannot contain a slash, so start it with --served-model-name.

Figure 3. Sequence trace of Claude Code driving tool executions via Ollama's Messages API endpoint.

The second pattern keeps Claude in the cloud and gives it a local model as a tool through the Model Context Protocol (MCP). Claude Code's MCP documentation shows how to register a local stdio server with claude mcp add. The server reads a file on disk, asks the local model to summarise or classify it, and returns only the result. Claude does the planning and hard reasoning, while bulk reading and private documents stay on your machine, as Figure 4 shows.

Tutorial 1: Your First Local Model In Ten Minutes Basic

Prerequisites: Ubuntu 22.04 or 24.04 (or Debian 12), NVIDIA GPU with 8 GB+ VRAM and proprietary driver installed, ≈10 GB free disk space.

This tutorial installs Ollama as a system service, downloads Gemma 4 E4B, an 8B model counting its embeddings, and talks to it from the terminal and over HTTP.

  1. Install Ollama and confirm the service is running.
  2. Pull the model and ask it a question.
  3. Call the native API and the OpenAI-compatible API with curl.
bash • tutorial-1.sh
# Step 1: install Ollama with the official script.
# The script installs the binary, creates an "ollama" system user
# and registers a systemd service that starts on boot.
curl -fsSL https://ollama.com/install.sh | sh

# Check that the service is active and print the installed version.
systemctl status ollama --no-pager
ollama -v

# Step 2: download Gemma 4 E4B (about 6.6 to 9.5 GB) and ask it a question.
# "ollama run" loads the model into VRAM and prints the reply.
ollama pull gemma4:e4b
ollama run gemma4:e4b "Explain what a systemd unit file is in two sentences."

# Step 3a: call Ollama's native chat API.
# "stream": false returns one JSON object instead of a token stream.
curl -s http://localhost:11434/api/chat -d '{
  "model": "gemma4:e4b",
  "messages": [{"role": "user", "content": "Name three Linux file systems."}],
  "stream": false
}'

# Step 3b: call the OpenAI-compatible endpoint that most tools use.
# Any OpenAI client library can point at http://localhost:11434/v1.
curl -s http://localhost:11434/v1/chat/completions   -H "Content-Type: application/json"   -d '{
    "model": "gemma4:e4b",
    "messages": [{"role": "user", "content": "Reply with the word ready."}]
  }'

# Confirm the model runs fully on the GPU: PROCESSOR should read "100% GPU".
ollama ps

Expected output: ollama -v prints a version number, the run command prints a two-sentence answer, and the second curl returns JSON whose choices[0].message.content contains "ready".

Troubleshooting: journalctl -e -u ollama shows the service log. If ollama ps reports CPU instead of GPU, run nvidia-smi; a missing driver is the usual cause. On Fedora, install the NVIDIA driver from RPM Fusion first; on Arch, use the nvidia package.

Tutorial 2: Connect OpenCode To A Local Model Basic

Prerequisites: Tutorial 1 completed. 24 GB GPU for Qwen3.8-27B, or 16 GB GPU for gpt-oss-20b.

OpenCode will read a small project and make an edit using a local model. The context window comes first, because OpenCode's prompts do not fit in Ollama's 4K default.

  1. Raise Ollama's default context to 64K through a systemd override.
  2. Install OpenCode and pull a coding-capable model.
  3. Write the provider block and run a first task.
bash • tutorial-2.sh
# Step 1: set a 64K default context for every model Ollama loads.
# The drop-in file overrides the packaged unit without editing it.
sudo mkdir -p /etc/systemd/system/ollama.service.d
printf '[Service]
Environment="OLLAMA_CONTEXT_LENGTH=65536"
'   | sudo tee /etc/systemd/system/ollama.service.d/context.conf
sudo systemctl daemon-reload
sudo systemctl restart ollama

# Step 2: install OpenCode with its official script.
curl -fsSL https://opencode.ai/install | bash

# Pull a model with native tool calling.
# 24 GB GPU: Qwen3.8-27B (18 GB). 16 GB GPU: use gpt-oss:20b instead.
ollama pull qwen3.8:27b

# Step 3: create the global OpenCode config directory.
mkdir -p ~/.config/opencode

Save the following as ~/.config/opencode/opencode.json. The ollama key is the provider ID, npm selects the OpenAI-compatible adapter, and each key under models must match a name from ollama list. The limit block tells OpenCode how many tokens the server accepts.

json • ~/.config/opencode/opencode.json
{
  "$schema": "https://opencode.ai/config.json",
  "model": "ollama/qwen3.8:27b",
  "provider": {
    "ollama": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Ollama (local)",
      "options": {
        "baseURL": "http://localhost:11434/v1"
      },
      "models": {
        "qwen3.8:27b": {
          "name": "Qwen3.8 27B (local)",
          "limit": { "context": 65536, "output": 16384 }
        },
        "gpt-oss:20b": {
          "name": "gpt-oss 20B (local)",
          "limit": { "context": 65536, "output": 16384 }
        }
      }
    }
  }
}
bash • first-task.sh
# Create a tiny project for the agent to work on.
mkdir -p ~/oc-demo && cd ~/oc-demo
cat > greet.py <<'EOF'
def greet(name):
    # Deliberately missing input validation for the agent to add.
    return "Hello, " + name
EOF

# Start OpenCode in this directory. Inside the TUI:
#   1. type /models and pick "Qwen3.8 27B (local)"
#   2. ask: "Add a check to greet() that raises ValueError for empty names,
#      then add a unittest file and run it."
opencode

Expected output: OpenCode lists the local model under /models, edits greet.py, writes a test file and runs it with Python, and the test passes.

Troubleshooting: If only cloud models appear, validate the file with jq . ~/.config/opencode/opencode.json. If the model answers in plain text instead of editing files, confirm the larger context took effect with ollama ps, which shows the context per loaded model.

Tutorial 3: Run Claude Code Against A Local Backend Intermediate

Prerequisites: Tutorial 2 completed, Ollama 0.14+, 24 GB GPU for Qwen3.8-27B.

Here Claude Code runs entirely against Ollama. A wrapper script keeps the local settings out of your normal shell, so plain claude still reaches Anthropic and claude-local reaches your GPU.

  1. Install Claude Code.
  2. Create a model variant with a 64K context baked in.
  3. Write the wrapper script and test an edit-and-run loop.
bash • tutorial-3.sh
# Step 1: install Claude Code with Anthropic's native installer.
curl -fsSL https://claude.ai/install.sh | bash

# Step 2: build a model variant whose context is fixed at 64K.
# A Modelfile layers parameters on top of an existing model.

Tutorial 4: Script Your Local Model From Python Intermediate

Prerequisites: Tutorial 1 completed, Python 3.10+, gpt-oss:20b pulled in Ollama (16 GB GPU).

Most local servers speak the OpenAI API, so the official OpenAI Python SDK works against all of them by changing one URL. This script streams a reply, measures tokens per second and runs one tool call against a real function.

  1. Create a virtual environment and install the SDK.
  2. Run the streaming benchmark.
  3. Run the tool-calling round trip.
bash • setup.sh

pip install --upgrade openai

python • local_client.py
"""Stream from a local model, measure speed, then run a tool call."""
import json
import shutil
import time

from openai import OpenAI

# Point the OpenAI client at the local server. Ollama ignores the key.
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
MODEL = "gpt-oss:20b"


def stream_and_measure(prompt: str) -> None:
    """Stream a reply and report time to first token and tokens per second."""
    start = time.perf_counter()
    first_token_at = None
    chunks = 0
    usage_tokens = None
    stream = client.chat.completions.create(
        model=MODEL,
        messages=[{"role": "user", "content": prompt}],
        stream=True,
        stream_options={"include_usage": True},  # final chunk carries token counts
    )
    for chunk in stream:
        if chunk.usage is not None:
            usage_tokens = chunk.usage.completion_tokens
        if chunk.choices and chunk.choices[0].delta.content:
            if first_token_at is None:
                first_token_at = time.perf_counter()
            chunks += 1
            print(chunk.choices[0].delta.content, end="", flush=True)
    end = time.perf_counter()
    # Fall back to counting streamed chunks if the server sent no usage data.
    tokens = usage_tokens or chunks
    gen_time = end - (first_token_at or start)
    print(f"

Time to first token: {(first_token_at or end) - start:.2f} s")
    print(f"Generated {tokens} tokens at {tokens / max(gen_time, 1e-6):.1f} tokens/s")


def disk_free_gb(path: str) -> dict:
    """The real function the model can call: free space at a path, in GB."""
    usage = shutil.disk_usage(path)
    return {"path": path, "free_gb": round(usage.free / 1e9, 1)}


TOOLS = [{
    "type": "function",
    "function": {
        "name": "disk_free_gb",
        "description": "Return the free disk space in gigabytes for a filesystem path.",
        "parameters": {
            "type": "object",
            "properties": {"path": {"type": "string", "description": "A path such as /"}},
            "required": ["path"],
        },
    },
}]


def tool_round_trip(question: str) -> None:
    """Ask a question, execute any tool the model requests, then get the answer."""
    messages = [{"role": "user", "content": question}]
    first = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS)
    reply = first.choices[0].message
    if not reply.tool_calls:
        print("Model answered without a tool:", reply.content)
        return
    # Keep the assistant turn, then append one tool result per call.
    messages.append(reply.model_dump(exclude_none=True))
    for call in reply.tool_calls:
        args = json.loads(call.function.arguments or "{}")
        result = disk_free_gb(**args)
        print(f"Tool call: {call.function.name}({args}) -> {result}")
        messages.append({"role": "tool", "tool_call_id": call.id, "content": json.dumps(result)})
    final = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS)
    print("Answer:", final.choices[0].message.content)


if __name__ == "__main__":
    stream_and_measure("Explain the difference between RAM and VRAM in 80 words.")
    tool_round_trip("How much free disk space is on / right now?")

Expected output: An 80-word explanation streams to the screen, followed by a time-to-first-token figure, a tokens-per-second figure, a line showing the disk_free_gb call with its result, and a sentence quoting the free space.

Troubleshooting: A 404 means the model name does not match ollama list. If the model answers without calling the tool, ask the question more directly. To point the script at LM Studio, vLLM or llama-server, change only base_url and MODEL.

Tutorial 5: Serve A 120B Model On Workstation Hardware Advanced

Prerequisites: NVIDIA GPU with 16 GB+ VRAM, 64 GB+ system RAM (96 GB ideal), ≈70 GB free disk, CUDA toolkit installed (nvcc --version).

gpt-oss-120b has only 5.1B active parameters, so most of its expert weights can live in system RAM while the attention layers and KV cache stay on the GPU. The --n-cpu-moe flag in llama.cpp sets how many MoE layers stay on the CPU, and the llama.cpp gpt-oss guide uses 32 for a 16 GB card.

  1. Build llama.cpp with CUDA and install it system-wide.
  2. Download the model and start llama-server with expert offload.
  3. Run it as a systemd service, then benchmark with llama-bench.

Tutorial 6: A Hybrid Local-Plus-Claude Workflow With MCP And Routing Advanced

Prerequisites: Tutorials 2 and 3 completed, Claude Code authenticated, Anthropic API key, and uv installed.

This tutorial builds both halves of Figure 4. First, an MCP server gives cloud Claude two local tools, so it can summarise and classify private files without the files leaving your machine. Second, a LiteLLM proxy and a short router script send each scripted request to the local model or to Claude.

  1. Write the MCP server with the MCP Python SDK.
  2. Register it with Claude Code and test it.
  3. Configure the LiteLLM proxy and run the router.
python • ~/mcp/local_llm_mcp.py
"""MCP server that exposes a local Ollama model to Claude as two tools.

Raw file contents are processed by the local model. Only the summary
or label that each tool returns is sent back to Claude.
"""
import json
import os
import urllib.request
from pathlib import Path

from mcp.server import MCPServer

# Local OpenAI-compatible endpoint and model; override with environment variables.
LOCAL_URL = os.environ.get("LOCAL_LLM_URL", "http://localhost:11434/v1/chat/completions")
LOCAL_MODEL = os.environ.get("LOCAL_LLM_MODEL", "qwen3.8:27b")
MAX_CHARS = 60_000  # cap input so the request fits the local context window

mcp = MCPServer("local-llm")


def ask_local(system: str, user: str) -> str:
    """Send one chat request to the local model using only the standard library."""
    payload = json.dumps({
        "model": LOCAL_MODEL,
        "messages": [
            {"role": "system", "content": system},
            {"role": "user", "content": user},
        ],
        "stream": False,
    }).encode()
    request = urllib.request.Request(
        LOCAL_URL, data=payload, headers={"Content-Type": "application/json"}
    )
    with urllib.request.urlopen(request, timeout=600) as response:
        data = json.load(response)
    return data["choices"][0]["message"]["content"]


@mcp.tool()
def summarize_local_file(path: str, focus: str = "key points and decisions") -> str:
    """Summarise a local text file with the on-device model and return only the summary."""
    text = Path(path).expanduser().read_text(errors="replace")[:MAX_CHARS]
    return ask_local(
        "You summarise documents accurately in under 200 words.",
        f"Focus on: {focus}

---
{text}",
    )


@mcp.tool()
def classify_text(text: str, labels: list[str]) -> str:
    """Classify text into exactly one of the given labels using the on-device model."""
    answer = ask_local(
        "Reply with exactly one label from the list and nothing else.",
        f"Labels: {', '.join(labels)}

Text:
{text[:MAX_CHARS]}",
    )
    return answer.strip()


if __name__ == "__main__":
    mcp.run()  # with no arguments the server speaks MCP over stdio

  num_retries: 2
  # If the local server errors, retry routine requests on Claude.
  fallbacks: [{"local-fast": ["claude-hard"]}]
python • ~/litellm/router.py
"""Pick a model group per task and send it through the LiteLLM proxy."""
from openai import OpenAI

# The proxy has no master key configured, so any placeholder key works locally.
client = OpenAI(base_url="http://localhost:4000/v1", api_key="sk-local-proxy")

HARD_HINTS = ("architecture", "prove", "refactor the whole", "security review", "design")


def choose_model(task: str, private: bool) -> str:
    """Private data stays local; hard or very long tasks go to Claude."""
    if private:
        return "local-private"
    if len(task) > 8000 or any(hint in task.lower() for hint in HARD_HINTS):
        return "claude-hard"
    return "local-fast"


def run(task: str, private: bool = False) -> str:
    model = choose_model(task, private)
    reply = client.chat.completions.create(
        model=model, messages=[{"role": "user", "content": task}]
    )
    return f"[{model}] {reply.choices[0].message.content}"


if __name__ == "__main__":
    print(run("Write a regex that matches Indian PIN codes."))
    print(run("Summarise this salary sheet: ...", private=True))
    print(run("Do a security review of this login design: ..."))

09Conclusion: Choosing Your Setup

Start from the hardware you have. A 16 GB card runs the 8B and 14B models, gpt-oss-20b and, with 64 to 96 GB of system RAM, gpt-oss-120b through expert offload. A 24 GB card is the point where Qwen3.8-27B makes local coding agents useful. For 70B dense models or several 120B MoE models, a 128 GB unified-memory machine gives capacity, while a GPU gives speed.

Before you buy, price your workload. If your team spends hundreds of dollars a month on Sonnet or Opus tokens for work a local model can handle, the break-even calculator will show a payback measured in months. If you mostly send short prompts that Haiku handles for cents, local hardware pays off only through privacy, offline access or the freedom to run unlimited batch jobs.

Then wire it in gradually. Begin with Ollama and OpenCode, move to Claude Code on a local backend for private repositories, and add the MCP server so cloud Claude can hand bulk reading to your GPU. Keep Claude for the work where its lead matters, and let the local model take the rest.
